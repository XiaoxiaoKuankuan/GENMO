连续滚动参考接管故障修复与原任务重放
====================================

本次仅修复连续滚动实验分支，两个正式基线工作目录保持不变。保留用户原运行
``stage2_rolling_NEW`` 的失败现场与initial checkpoint。服务器1采用原配置、
Stage1 s595000、同一组32个MC任务、相同音乐起点及随机种子重放，未更新网络。

实际故障原因
------------

问题任务为FineDance 074，seed=31415，音乐起点890帧，env0。时刻均是episode
重置后的真实仿真时间，包含前1秒运动初始化预热，不是音乐文件的绝对位置。

* 1.00秒请求的第一份参考，拼接检查窗口内最大刚体姿态相邻变化0.3632207 rad，
  超过原有0.35 rad上限，prepare拒绝，旧bootstrap保持权威。
* 1.30秒请求的第二份参考，相同指标0.4305740 rad，再次拒绝，旧参考仍未被清空。
* 1.60秒第三次请求在修复后通过prepare，但实际到达为1.86秒，已经赶不上旧窗口。
* bootstrap的60帧覆盖包含预热；源末尾1180 tick、有效50Hz参考末尾1164 tick
  （1.94秒）。GMT还有0.2秒前瞻，旧参考能够支持的中心不超过1.74秒。
  原程序把“前瞻可以改写”误写成“等待不需要前瞻余量”，在1.76秒读取至1.96秒而崩溃。

原失败现场只能直接证明env0仍执行bootstrap、env1已有新计划、1.76秒发生越界。
上述两次具体拒绝及第三次到达，是相同任务和噪声种子的修复后真实PhysX重放证据。
第三次请求临近边界的deadline/前缀受本次修复影响，不冒充旧运行第三次候选逐位复现。

实现与边界
----------

* ``vector_environment.py``：等待新Motion时始终保留120 tick前瞻、右插值及差分支持。
  滚动末尾deadline落在60 tick共同格，最坏提交拒绝时仍可产生合法终态条件。
  本例在1.70秒正常行政截断；这是旧参考真的即将用尽，并非每0.3秒截断一次。
* ``env_adapter.py``：prepare成功但commit失败时重核旧参考边界。成功提交立即应用ACK
  中的权威范围，避免恰在下一决策格提交、没有额外物理步刷新快照时仍按旧尾误截断。
* GMT ``closedloop_reference.py``：成功提交返回紧凑 ``reference_state``，包含真实新范围，
  不加入新Actor观测、不推进物理。幂等回复保持首次成功的提交状态。
* ``reference_lifecycle.py`` / ``world_collector.py``：每环境仅保留最近32事件，拒绝、
  截断或异常时保存紧凑JSON；即使MC episode尚未结束，也能追溯为何没有接管。
* ``vector_evaluation.py``：关闭失败不再替换执行的原始异常，另存cleanup错误。
  正常执行后的异常关闭仍严格报错。该异常报告修正以CPU回归验证，未在物理中故意制造
  新故障；其余实际接管修复使用GENMO f1ed0d1、GMT 25062a9完成下面重放。

旧Motion直到成功commit前始终保留。没有添加静止补尾、混合过渡、放宽拼接阈值，
没有修改Actor/GMT权重、PPO目标、奖励、物理时钟或已知前缀mask。
参考行政截断的3个上层状态被完整MC bank明确排除，不伪装成真终止的完整MC标签；
普通训练仍沿用既有行政截断自举及重新抽取任务机制。

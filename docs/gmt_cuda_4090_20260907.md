# GMT 本地 RTX 4090 接入与验收记录（2026-09-07）

## 1. 结论和边界

现有 `noetic` 容器已配齐隔离的 CUDA 版 ONNX Runtime，当前部署控制器已经重新编译。
显式 `gmt_onnx_provider:=cuda` 可使 GMT 使用本地 RTX 4090；默认仍使用原 CPU 运行库，
WALK/DANCE/GMT_FUTURE 不注册 CUDA。GENMO 的 Bridge、Console 和生成模型命令均不改变。

本轮完成了原生 C++ CUDA 推理、逐帧数值对比、算子执行后端确认、WALK CPU 回归和故障检查。
没有启动 Gazebo、ROS 控制节点、Bridge、Redis 或实物控制；launch 仅静态解析。
没有改变 2000 Hz 基础频率、分频 40、原显式 PD、增益、延迟、关节顺序、模型或轨迹。

GPU 可用不等于更快：最终测试旧 CPU 平均 0.455 ms、CUDA 平均 0.493 ms，CUDA 约慢 8.4%。
CUDA 的本次尾部耗时较低，但不能从有限独立测试推广为稳定的实时性保证。
这次没有证明完整部署链路能达到真实 50 Hz，也不能据此认定仿真中的具体瓶颈已被定位。

完整逐轮数值、实际库路径、模型指纹、Profile 汇总和故障消息见
[机器可读验收报告](gmt_cuda_acceptance_20260907.json)。

## 3. 修改了什么，为什么修改

### 会话配置和推理错误处理

- 新增 `include/rl_controllers/GmtOnnxRuntime.h`：部署与独立探针共用会话配置、设备检查、
  实际运行库路径输出、预热及动作有效性检查。
- `AcController.cpp`：读取 `/gmt_onnx_provider` 和 `/gmt_cuda_device_id`，为 GMT 单独创建会话；
  WALK/DANCE/FUTURE 仍使用原有未注册 CUDA 的 CPU SessionOptions，不更改 CPU 线程设置。
- CUDA 使用 V2 Provider Options：`device_id=0`、`use_tf32=0`、`do_copy_in_default_stream=1`、
  `enable_cuda_graph=0`。不启用 FP16、TensorRT、自定义 stream、IO Binding 或异步控制线程。
- CUDA 会话初始化时用临时零输入预热 20 次，结果丢弃，不修改真实动作缓存、历史观测或机器人命令。
- 显式 CUDA 请求下，错误运行库、无效设备、模型缺失、Provider/预热失败会阻止初始化，
  不静默改成 GMT CPU 推理。启动日志包含实际 ORT 文件、版本、设备名称/UUID、模型及 I/O。
- `computeActionsGmt()` 及基类/派生类声明从 void 改为 bool；输入构造、Run 和输出检查统一捕获异常。
  输出必须为完整 FP32 `[1,动作数]` 且全部有限，验证通过后才能更新动作缓存。
- 推理失败后立即切 WALK、调用 WALK 处理并退出 GMT 分支，不再裁剪/发布/下发旧 GMT 动作，
  不增加成功策略帧诊断。状态分支采用静态检查，未做含真实硬件句柄的控制器实例测试。

Redis 数据协议没有修改。原接收 ACK 在读取/接收轨迹时产生，不等于策略推理成功或电机执行成功；
本轮不把接收 ACK 当作执行证明，也没有重新设计 ACK 协议。

### 编译和动态库选择

- `CMakeLists.txt` 增加显式 `ONNXRUNTIME_ROOT`，采用同一发行目录的头文件和原生库。
  新增原生探针及输出检查测试目标，使用可被启动环境覆盖的 RUNPATH。
- `RLControllerBase.h`、`GmtController.h` 的 ORT include 统一为无目录前缀形式。
  原 `<onnxruntime/onnxruntime_cxx_api.h>` 会绕开新 include 路径并命中旧 CPU 头文件，
  与官方 GPU 头文件同时出现时造成重复定义；这里只统一 include，不改变旧 GmtController 的策略行为。
- `ac_start.launch`、`ac_start_real.launch` 在包含 Gazebo/硬件进程之前设置库路径；
  `load_ac_controller.launch` 接收并发布两个新参数。不能只给 controller_spawner 设置环境。
- `simulation.sh`、`real.sh` 同步使用说明，原入口行为与参数透传保留；`simulation_buffered.sh` 无需修改。

实施中实际发现两份同为 1.19.0 的 ORT 使用不同 SONAME：

| 文件 | 实际 SONAME |
|---|---|
| 原 `/usr/local/lib/libonnxruntime.so.1.19.0` | `libonnxruntime.so.1.19.0` |
| 官方 GPU 包主库 | `libonnxruntime.so.1` |

因此仅将 `/usr/local/lib` 放在前面并不能保证默认加载旧 CPU 库。安装脚本在验证旧库版本后，
额外建立隔离的 `cpu/lib` 同版本别名，指向原 CPU 文件；不是把不同 CUDA/cuDNN 主版本伪装成兼容版本。
不修改原 CPU 文件或官方 GPU 原包。

- CPU 入口：`/usr/local/lib`、隔离 `cpu/lib` 优先，实际加载路径已验证为原 CPU 库。
- CUDA 入口：隔离统一 `lib` 优先，实际加载路径已验证为官方 GPU 库。
- CUDA 进程只使用一份 GPU 版 ORT，GMT 选 CUDA EP，WALK 等选 CPU EP。
- 切换需要重启承载控制器的进程，不能在已有 gzserver 中只热加载控制器来改变库版本。

依赖检查时 CUDA Provider 的 `Provider_GetHost` 来自同包 Shared Provider；
脚本按 ORT 加载语义预加载同包 Shared 再执行 `ldd -r`，而不是忽略未解析符号。
23 个库入口完成依赖及符号检查，随后又通过真实 C++ CUDA 会话验证。

### 测试工具

- `scripts/setup_gmt_cuda_runtime.py`：固定版本安装、校验、安全解包、同版本 CPU 别名、幂等验证。
- `test/gmt_onnx_probe.cpp`：原生 FP32 推理、种子 42 的同输入语料、逐帧输出、同步计时和独立 Profile。
- `scripts/verify_gmt_cuda.py`：顺序运行三种后端组合、WALK 回归、六类故障、launch/失败分支静态检查，
  汇总 JSON。NVML 在容器内可能返回宿主 PID，显存采样使用唯一新增计算进程匹配，歧义时记未知。
- `test/test_gmt_onnx_failure.cpp`：无 ROS 节点的非法 Provider、空输出、错维度、NaN/Inf 检查。
  不实例化构造时含 TF 广播器的控制器，避免独立测试隐式启动 ROS 通信。

## 4. 最终验证结果

### 编译和运行库

- `rl_controllers` 使用官方 GPU 头文件/库重新编译成功；最后一次编译 8.5 秒，未重编物理插件。
- 新增输出检查 gtest：1 个测试通过，覆盖多种输入/输出错误。
- 安装脚本重复验证成功；原 CPU 库 SHA256 保持
  `6bf232956b875e0dd4b7cb8334eb3401ae23d354c147f7e51d16ce1389a002dc`。
- 最终控制器库 SHA256：`0e0095d6302990f15870ab0c3b3acfd299a58a23b3915ffafb5f24501be8f936`。
- 物理插件 SHA256 仍为 `e7b19ad993f6d515f9915f87b689884ec7ac0e2ff3e0934500c25cd0257be6c2`。
- CPU/CUDA × online/offline/buffered 的 6 个仿真 launch 解析通过；实机 CPU/CUDA 2 个解析通过。
  仿真仍 2000/40、0.5 秒过渡、原显式 PD、无绘图/CSV；实机仍 500/10、2 秒过渡。

### 模型与数值

模型 `model_135000_stage2.onnx` 的 SHA256 为
`d2e176657d72d1b0efcb04406abd17145fc45a3a5755b62aae7b866e0a6e3d1b`，测试前后相同。
输入仍为 `policy[1,69]`、`history_obs[1,690]`、`command_window[1,1092]`，输出 `actions[1,21]`。

固定 1000 组输入，共比较 21000 个输出值，阈值为 `abs(candidate-cpu) <= 1e-4 + 1e-4*abs(cpu)`：

- 原 CPU 与新 ORT 的 CPU EP：最大误差 0。
- CPU 与 CUDA：最大误差 `4.649162292480469e-6`，平均误差 `5.27799979040754e-7`，超限 0。
- WALK 原 CPU 与新 ORT 的 CPU EP：21000 个值最大误差 0。

Profile 中 1360 次主要矩阵算子事件均在 CUDA，CPU 主要矩阵算子事件为 0；
本次记录的有 Provider 标记的算子均为 CUDA。不是只看显存或可用 Provider 列表判定成功。

### 性能

最终在本任务编译全部结束后顺序测试；各组额外预热 100 次，2000 次×3 轮，
使用相同的 0.5 秒显存监测间隔。计时包含主机输入包装、同步 Run、CPU 输出读取和有效性检查，
没有开启 Profiling。输入是合成语料，不是仿真反馈录制。

| 后端 | 6000 次平均 | 三轮 P99 最大值 | 单次最大值 | 超过 20 ms |
|---|---:|---:|---:|---:|
| 原 CPU ORT | 0.455 ms | 2.470 ms | 6.716 ms | 0 |
| 新 ORT 的 CPU EP | 0.555 ms | 4.932 ms | 9.551 ms | 0 |
| 新 ORT 的 CUDA EP | 0.493 ms | 1.591 ms | 4.970 ms | 0 |

CUDA 进程采样显存峰值 474 MiB；这是 0.5 秒间隔观测值，不是严格捕获所有瞬时分配的峰值。
各组均是单独 GMT 会话，不包含生产中其它会话、物理引擎、Redis、硬件读写或 GENMO 并发负载。
不能把此表换算为机器人实际控制频率，也不能保证后续每次都没有超过 20 ms 的调度抖动。

开发中间轮曾与测试目标编译重叠，原 CPU 出现过 22.65 ms 单次耗时；该轮不作为最终性能基线。
它也说明一般 Linux 调度下不能用一次短测试宣称硬实时保证。最终复测记录全部三轮，没有只挑最快一轮。

### 故障验证

以下六类故障均以非零退出并输出具体错误，没有静默 CPU 降级：非法 Provider、无效 GPU 设备、
请求 CUDA 却加载旧 CPU 库、模型不存在、输入维度错误、隐藏 CUDA 用户态依赖。
最后一项通过子进程库路径隔离模拟，实际报 `libcublasLt.so.12` 缺失，未删除正式库。
控制器失败后跳过旧动作下发/成功诊断的分支顺序通过源码静态检查；不宣称经过真实闭环故障注入。

## 5. 现在怎么启动

本机已经安装、编译完成，正常使用不用重新编译。进入已有容器的部署目录：

```bash
cd /host/Documents/bumi_GMT_deployment_obs
```

普通在线入口，仅 GMT 使用 GPU：

```bash
./simulation.sh gmt_onnx_provider:=cuda gmt_cuda_device_id:=0
```

整段缓存独立播放入口，仅 GMT 使用 GPU：

```bash
./simulation_buffered.sh gmt_onnx_provider:=cuda gmt_cuda_device_id:=0
```

原命令不带参数仍使用 CPU，也可显式指定：

```bash
./simulation.sh gmt_onnx_provider:=cpu
```

独立播放模式回到 CPU 时使用 `./simulation_buffered.sh gmt_onnx_provider:=cpu`。
切换前后都需要重启仿真进程，不能让旧进程继续运行来判断新设置。
启动后应看到 `requested=cuda`、隔离 ORT 实际路径、`NVIDIA GeForce RTX 4090`、
`CUDA registered` 和 `warmup=20 passed`。CPU 模式日志应显示原 `/usr/local/lib` 文件。

以上启动命令是交付用法，本轮没有执行。实机入口只增加了相同参数，未做实机运行验证；
其它实物计算板，特别是 ARM/Jetson，不能直接使用本次 x86_64 二进制包。

## 6. 复现检查与回退

在容器部署目录中，检查已安装依赖：

```bash
python3 -B src/legged_rl/rl_controller/rl_controllers/scripts/setup_gmt_cuda_runtime.py --verify-only
```

重新安装时去掉 `--verify-only`；只复用清单完全一致的安装，不覆盖未知内容。
需要重新编译时：

```bash
source devel/setup.bash
catkin build rl_controllers --no-deps --no-status -j 4 --cmake-args -DONNXRUNTIME_ROOT=/opt/bumi-gmt-ort/1.19.0-cu124-cudnn9/ort -DCMAKE_BUILD_TYPE=Release
```

独立复测，不启动机器人：

```bash
source devel/setup.bash
gmt_verify_dir=$(mktemp -d /tmp/gmt_cuda_verify.XXXXXX)
python3 -B src/legged_rl/rl_controller/rl_controllers/scripts/verify_gmt_cuda.py --output "$gmt_verify_dir/report.json"
```

工具自动清理内部原始轨迹/Profile/日志，只保留明确指定的汇总报告。
不要在训练、编译或仿真同时占用资源时把测得时延当作空载基线。

旧控制器可恢复副本保存在容器 `/opt/bumi-gmt-ort/backups/pre-cuda.hMQQYY/`：
`librl_controllers.so` 的 SHA256 为 `d6511ef9391bc1fb68a674bd921f3b32c2f62ce8cdd39074640a7ac57617524b`，
`source-before.tgz` 保存主要修改文件的任务前状态。仅切回 CPU 无需恢复这些文件或卸载依赖。
不提供覆盖整个工作树的回退操作，以免破坏用户其它有效改动。

依赖安装在现有容器可写层，删除容器会丢失；重建容器需重新安装，或显式用原 CPU 根目录重编。
不能只复制 GPU 链接的 devel 产物、遗漏运行库及 CPU 兼容入口。

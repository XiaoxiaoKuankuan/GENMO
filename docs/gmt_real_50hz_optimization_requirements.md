# BUMI GMT 部署真实 50 Hz 优化需求与现状分析

版本：2026-09-07，需求与技术分析初稿。交接对象：部署、C++ 控制、ROS/Gazebo 和性能优化开发人员。

本文针对用户通过 `./simulation.sh` 运行的 BUMI Gazebo 仿真部署链路。目标是让 GMT 闭环在真实时间内稳定完成每秒 50 次有效策略更新，并使仿真与正常速度音乐保持时间一致。不是把配置文件再改成一个“50”，也不是只提高 Redis 发送次数。

本次完成了源码/配置/历史日志核验，以及不连接 ROS、Redis、Gazebo 或电机的独立 C++ GMT 推理基准。没有实施下文的性能优化，没有启动仿真或实机。因此本文不是“已经达到真实 50 Hz”的验收报告。

## 1. 可以直接发给负责人的问题摘要

当前 Gazebo + GMT 部署按 `2000 Hz 基础更新 / 40 次降采样 = 50 Hz 策略更新` 配置，但这个 50 Hz 跟随仿真时间，并不自动保证每个真实秒执行 50 次。

此前在线运行的记录估算为：Bridge 在真实时间内发布约 50 包/秒，GMT 消费策略约 28.85 次/真实秒，仿真实时率约 0.577。参考动作按真实时间推进，机器人动力学与策略却慢速推进，两者因而错位；转身等快速变化处尤其明显。离线按仿真步取轨迹，较不容易发生这种参考时间轴错位，但离线效果较好不能证明离线已经达到真实 50 Hz。

需要优化的是整个部署闭环的实时执行能力：物理仿真、控制回调、状态处理、参考数据接收、GMT 推理、指令提交以及非必要的调试开销。**现有证据不足以把主因单独归咎于 ROS1、Redis、网络带宽或 GMT 模型推理。** 本次独立基准中实际 GMT 模型的平均推理耗时约 0.35～1.26 ms，不能把历史平均 34.7 ms 的策略间隔直接解释为模型推理耗时。

交付要求：给出可复现的分段耗时证据，找到主要瓶颈，完成针对性优化，并在同一模型、机器人、轨迹及生成并发负载下，通过真实时间 50 Hz、抖动、数据新鲜度和仿真实时率的联合验收。

## 2. 优化范围、优先级与禁止混淆的目标

### 2.1 必须完成

1. 先补齐计时与诊断，能够回答“一个真实控制周期的时间花到哪里去了”。
2. 保留现有 GMT 策略和运动数据语义，优化 C++ 执行链、通信隔离、线程调度与非控制开销。
3. 在 Gazebo 中达到稳定的真实时间 50 Hz 策略更新，同时维持接近 1 的仿真实时率。
4. 分别验证离线 NPZ、整段缓存、实时参考三条消费链；最终验证与用户的 CUDA 在线生成同时运行。
5. 形成可重复启动、可验证已加载新库、可回退、可自动统计达标情况的交付包。

### 2.2 不是本次优化的替代品

- 只把 `fps`、`control_frequency`、`decimation`、定时器或日志中的数值写成 50。
- 只证明 Bridge 发布 50 包/秒，或只证明 ONNX 单独能够每秒推理超过 50 次。
- 仿真慢速运行，但用缓存保证每次策略更新只取下一帧。这能解决时间轴错位，不代表真实 50 Hz。
- 重复发送旧动作、跳过参考帧、缩短整段舞蹈、删除困难动作，以伪造频率或流畅度。
- 仅关闭窗口后空载通过，却没有用户日常运行配置和 GENMO 并发场景的结果。

### 2.3 保持不变的契约

未经专项批准，不修改策略权重、关节顺序、动作缩放、PD 增益、限位、世界/机体坐标约定、四元数顺序、中心差分根角速度、历史堆叠布局和参考窗中心语义。

第一阶段也不修改物理步长、碰撞/惯量/摩擦、接触求解参数及模拟指令延迟。若测量证明必须调整物理配置，需要另列动力学影响和闭环回归，不能只以 RTF 上升作为成功证据。

Gazebo 达标不等于实机安全；实机 500 Hz 基础循环、EtherCAT 和电机链路必须另行验收。本需求不授权启动电机或绕过现有保护。

ROS1 的默认跨进程可靠订阅与 TCPROS 协商可在 [Noetic roscpp 源码](https://raw.githubusercontent.com/ros/ros_comm/noetic-devel/clients/roscpp/src/libros/subscription.cpp) 中核对。这里没有证据说明改成 ROS2 或 UDP 就能直接消除瓶颈。

Redis 轨迹不是 ROS topic，也不是逐关节 JSON 文本。`trajectory_v1` 包含 104 字节头和 `110×55` 个 float32，合计 24,304 字节；50 包/秒约为 1.22 MB/s 的单向应用层数据。经过 Redis 的 SET、GET 及 TCP 开销另算。这个量级本身不能证明网络带宽不足，必须测量请求延迟、排队、复制和线程等待。

实时包魔数是 `OMGBT001`，ACK 为 `OMGBTA01`；数据包含关节顺序哈希、CRC、身份与序号。55 维一帧为根位置3、wxyz四元数4、机体系根线/角速度各3、关节位置21、关节速度21。接收器抽取过去10/当前1/未来10，形成 `21×52` 策略参考窗。

### 3.3 真正的策略输入，不只是“52维”

本次直接读取实际 ONNX 文件并与已有加载日志核对：

| 输入/输出 | 形状 | 意义 |
| --- | --- | --- |
| `policy` | `[1,69]` | 当前机器人重力投影3、角速度3、关节位置21、关节速度21、上次动作21 |
| `history_obs` | `[1,690]` | 10步观测历史，当前配置为 term-major 布局 |
| `command_window` | `[1,1092]` | 21帧×52维参考，包含根高度、重力投影、根速度、关节位置/速度 |
| `actions` | `[1,21]` | GMT 输出动作 |

因此，“在线离线 52 维参考逐帧一致”只是必要条件。两次闭环的当前状态、历史观测、上一动作或时间对齐不同，最终动作仍会不同。性能优化的数值回归必须覆盖三个完整输入与 actions，不能只比较 NPZ 和 Redis 的关节角。

用户的 `--onnx-provider cuda --ddim-steps 20` 控制的是 GENMO 音乐动作生成器，不是 C++ GMT 执行后端。当前 `AcController::loadModel()` 未注册 CUDA EP，只设置 `SetInterOpNumThreads(1)` 后创建会话，走默认 CPU EP 的代码路径。需要由部署启动日志明确输出实际后端，不要用生成器的参数推断 GMT 在 GPU 上运行。

## 4. 50 Hz、仿真时间与真实时间到底是什么关系

### 4.1 当前周期怎么产生

1. `empty_world.world` 设置物理步长 `0.0005 s`，即每计算一次，物理状态的时间坐标向前推进 0.5 ms。
2. Gazebo 为求出这一步状态，实际可能计算、等待或被调度超过 0.5 ms；这个真实耗时由电脑运行情况决定。
3. 当前 URDF 没有另设 `controlPeriod`；标准 gazebo_ros_control 默认采用物理步长作为控制周期，基于 Gazebo 仿真时间调用更新。
4. `AcController` 每40次基础更新计算一次 GMT：`40×0.0005=0.02 s`，所以是50次/仿真秒。
5. 只有这40步物理/控制计算及相关等待合计能在真实20 ms左右完成，才同时得到50次/真实秒。

Gazebo 的步长和目标更新率并非计算完成时限的保证；控制插件的仿真时间调度与默认周期也可直接查看 [Noetic gazebo_ros_control 实现](https://raw.githubusercontent.com/ros-simulation/gazebo_ros_pkgs/noetic-devel/gazebo_ros_control/src/gazebo_ros_control_plugin.cpp)。

定义：`RTF = 仿真时间增量 / 真实时间增量`。稳定按仿真50 Hz调度时，有 `实际策略频率 ≈ 50×RTF`。这来自当前调度关系，不是说所有机器人软件都只能以仿真时间计时。

```text
相邻两次策略调用之间：
  仿真推进：40个物理步 × 0.5 ms = 20 ms
  真实耗时：40步物理计算 + 40次基础控制工作
           + 1次GMT参考/观测/推理工作 + 调度与等待

例如真实耗时约34.7 ms，仿真仍只前进20 ms：
  RTF约0.577，GMT约28.85次/真实秒。
```

`34.7 ms` 是两次策略调用之间的平均真实间隔估计，不是测出来的 `Ort::Session::Run()` 单函数耗时。

### 4.2 在线、离线与缓存模式的差异

| 模式 | 参考进度由谁推进 | 仿真变慢后的表现 | 是否自动解决真实50 Hz |
| --- | --- | --- | --- |
| 实时在线 | Bridge 的真实时间发布节奏 | 最新参考比机器人仿真推进快；GMT GET 可能跨过多个发布序号 | 否 |
| 离线 NPZ | GMT 每次策略更新推进固定轨迹时间 | 动作随仿真一起变慢，参考与仿真较一致 | 否 |
| 新增 buffered | GMT 每次策略更新消费本地缓存下一帧，Bridge 跟随ACK | 避免按网络心跳跳过动作，暂停仿真时不推进 | 否 |

实时 Redis 使用“最新值键”，不是自动保留每一帧的队列。当生产端50次/真实秒、消费端约29次/真实秒时，看到发送序号跳跃首先说明消费没有逐包覆盖，不能直接称为 TCP 丢包。

buffered 模式已有说明见 [整首预生成与缓存播放文档](bumi_buffered_gmt_playback.md)。它仍有心跳 GET/ACK 和校验开销，只是完整轨迹已在本地，不是一个已经完成的底层实时性优化。其自动音频播放目前关闭，不能把“缓存动作正确播放”宣传为正常速度音乐同步通过。

### 4.3 轨迹时长与模型内建延迟

实际离线文件 `C/motion_files/bumi/bumi/mine_bumi__dance_3__火力全开.npz` 为3301帧、50 Hz：首末样本跨度 `(3301-1)/50=66.00 s`，MotionLoader 按 `N/fps` 打印 `66.02 s`。两者只差末帧区间的定义。

如果整首平均RTF一直为0.577，66秒仿真轨迹理论上会花约114.4秒真实时间。这只是按固定RTF推算，不能当作已经实测的整首完成时间；必须排除准备、缓入、返回、暂停和尾部保持后单独计时。

还发现当前 `B/legged_gazebo/config/bumi3_4340.yaml` 设置了 `gazebo.delay: 0.009`。`LeggedHWSim::writeSim()` 用带仿真时间戳的队列模拟约9 ms指令延迟，之后再做PD力矩计算。这是模型主动模拟的延迟，**不是网络测出来的9 ms，也不是线程 sleep 9 ms**。不允许为了变快悄悄删除；测动作实际生效时间时必须单列此延迟及步长量化。

### 5.3 本次独立 C++ GMT 推理基准

方法：在同一 `noetic` 容器，用现装 C++ ONNX Runtime 1.19.0、CPU EP 和实际 `model_135000_stage2.onnx`；同时创建并驻留 walkrun、policyDance、GMT三个会话，只有GMT执行推理。`inter_op=1`，分别测试默认/1/2/4个算子内线程。输入为按真实形状预分配的全零float32，连续预热30次后计时1000次同步Run，单调时钟计时，逐次确认输出有限。

| 默认0，保持当前配置语义 | 0.348 | 0.308 | 0.488 | 1.188 | 3.458 | 0/1000 |
| 1 | 1.262 | 1.250 | 1.392 | 1.525 | 2.592 | 0/1000 |

| 4 | 0.518 | 0.499 | 0.610 | 0.806 | 1.438 | 0/1000 |

预检查另做了默认线程400次，平均0.421 ms、P99 3.127 ms、最大5.881 ms，同样没有超过20 ms。两次差异提醒：短基准存在调度波动，不能据此选定最终线程数或宣称尾延迟已保证。

可得结论：此模型在本次无Gazebo/GENMO并发的独立固定图测试中，不是每次Run都要30多毫秒。限制：全零输入、连续热运行、预分配输入，不包含实际观测构造、50 Hz休眠唤醒、网络、物理/接触、GUI、线程竞争或控制库调用包装；也未计入模型加载。不能从此表证明闭环已达标，或直接认定单线程/四线程一定更好。

临时基准源码、可执行程序及主机/容器临时目录已在本次审计清理；没有向生产Redis键写入动作，也没有改部署库。后续正式交付应将可复用基准程序纳入测试源码，并保留其run配置与原始样本。

## 6. 从代码能定位到的具体风险

### 6.1 P0：关键路径缺乏真实周期与分段耗时诊断

`AcController::handleGmtMode()` 依赖基础循环计数并累加固定 `dt_policy`。`gmt_policy_sequence` 可以计数，但现有诊断没有完整记录策略实际开始/结束、Run开始/结束、动作提交以及每40步的物理成本。

现有绘图/CSV由另一个ROS节点采样多个topic，不是同一次控制迭代的原子快照；可能漏采或重复采样，不能用CSV行数当策略执行次数。频率计算必须以控制线程产生的序号和单调时间戳为准。

当前 `gmtRedisTimeout=0.2` 约束的是“距离最近接收有效数据的时间”，不是一个真实50 Hz执行保证；缺少明确的20 ms截止期监控与分级诊断。

### 6.2 P1：2000 Hz循环承载了大量非控制发布与动态内存操作

`RLControllerBase::updateStateEstimation()` 每次基础更新直接发布7类状态数据；`update()` 再发布3类计划量及controller_mode，合计11个显式publish调用。按照配置约为22,000次publish调用/仿真秒，尚不包含TF、GMT诊断和Gazebo自身topic。

同一循环还反复构造Eigen动态向量、消息数组、关节名字映射和 `std::map`，并调用 `publishFixedTransforms(true)`、动态关节TF及world→base TF。静态TF没有必要每0.5 ms重新准备发布。

这些调用不等于每个消息都实际发上网络；无订阅者时ROS可能省去部分传输。但消息构造、映射和某些序列化/调度工作仍可能发生。特别是当前绘图节点订阅了多条高频topic，降下游CSV采样率并不会自动降低上游2000 Hz发布成本。

这是高优先级候选瓶颈，不是已测得的主因。要求按“状态读取/必要估计”和“遥测/TF/绘图”拆分计时，先测关闭绘图订阅的收益，再实现上游主动降频、预分配及异步日志，并保留必要的监控信息。

### 6.3 P1：策略线程中同步执行Redis请求，且未发现套接字超时设置

调用顺序是 `handleGmtMode → MotionLoaderRedis::update → redisCommand(GET) → 校验/解码 → redisCommand(SET ACK)`，之后才执行观测和策略计算。连接/重连也使用同步 `redisConnect()`。

本次检查该接收器未找到 `redisConnectWithTimeout()` 或 `redisSetTimeout()`；`timeout_s_` 只用于数据新鲜度检查。也就是说，文件里写了0.2秒数据超时，并不代表同步GET会在0.2秒、更不代表在20毫秒以内返回。hiredis区分同步与异步接口，见 [hiredis官方说明](https://github.com/redis/hiredis#synchronous-api)。

正常本机Redis往返可能很快，但Redis卡顿、重连、服务阻塞或调度延迟会直接拉长当前控制回调，甚至拖住整个仿真步。这是可从代码确认的实时性风险；本次没有生产Redis延迟分布，不应写成“已经测出Redis导致了42%的性能损失”。

要求：接收/校验/ACK移到非控制工作线程；控制线程只读取已经验证、完整且有明确身份的本地快照。网络超时和重连退避单独配置；缓存交换不得形成无限等待或数据竞争。保留CRC、关节顺序、序号、会话、过期保护，不靠删校验提速。

注意：现有ACK在数据接收路径产生，不能直接证明对应GMT推理已完成或动作已生效。需要区分 received、selected、inference_done、command_committed、applied 各阶段；若改变ACK语义，须显式协议版本化并兼容Bridge。

### 6.4 P1：ONNX线程配置容易被误读，需联机而不是只测裸Run

现有 `SetInterOpNumThreads(1)` 不等于整个模型只使用一个CPU线程。算子内线程数未显式设置，会话还可能维护各自线程池及自旋等待。inter-op和intra-op含义不同，见 [ONNX Runtime线程说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。

因此需要扫描intra-op、会话共享线程池/闲置会话、自旋开关、CPU亲和性，并同时记录gzserver物理线程与ROS/绘图负载。本次表格只说明CPU推理有余量，不支持先行将GMT切换GPU；GPU还可能与GENMO生成争用，数据传输和同步也可能增加尾延迟。

`computeActionsGmt()` 每次构造输入包装、形状/容器和输出接收，`computeObservationGmt()` 还构造参考窗、历史和动态数组。这些开销应与Run本身分开测量，再做预分配/减少复制。当前构建已经是Release，不要把“改成Release”当成未经核验的首要修复。

线程参数必须以实际ORT 1.19.0 API支持为准，不照搬新版本文档中未确认兼容的配置键。选择依据是闭环周期P99和RTF，而不是单独Run的最快平均值。

### 6.5 P1/P2：物理、接触与仿真硬件接口成本需要独立量化

`LeggedHWSim` 每个物理步读取关节/IMU，遍历接触信息，按关节名字查找延迟队列并生成PD力矩。启用了 `SetNeverDropContacts(true)`；机器人另有500 Hz ground_truth插件。无GMT推理时，这些工作也在运行。

必须比较：裸世界、同机器人站立但不执行GMT、离线GMT、在线GMT。若没有推理时RTF已经明显低于1，应优先查物理、接触、基础控制/TF，而不是继续优化生成模型。

`empty_world.world` 将 `<type>world</type>` 和 `<iters>2000</iters>` 直接放在 `<physics>` 下；ODE求解器的对应设置通常位于 `physics/ode/solver`，且iters只对quick求解器有意义。见 [Gazebo物理参数说明](https://classic.gazebosim.org/tutorials?tut=physics_params)。因此不能仅看这两行就断言“实际使用world求解器、每步迭代2000次，所以慢”。

本次 `gz sdf -k` 返回 `Check complete`，但这不等于运行时采用了用户想要的求解器数值。正式采集必须导出解析后的SDF和实际physics属性/求解器设置；当前没有运行中的Gazebo，实际生效值仍待核验。修改层级本身也可能改变动力学，不在本轮直接修改。

### 6.6 P2：调度与资源竞争，不能只看整机CPU百分比

多核CPU总占用不高，仍可能有单个物理线程已满或频繁被抢占。GENMO CUDA生成也可能占CPU做特征、后处理、拷贝和线程池工作。

需测每线程CPU时间、上下文切换、运行队列等待、核心迁移、page fault、频率/温度；核对容器资源限制和实际亲和性。当前Docker没有显式限额，并不能排除主机其他程序竞争。本轮没有证据证明容器NAT导致慢，因为容器实际使用host网络。

CPU隔离、优先级和实时内核可作为后续选项，但须有收益数据及看门狗设计。不能直接给全部进程最高优先级；也不能把实机 `LeggedHWLoop` 中的SCHED_FIFO设置误认为Gazebo线程已经采用同样调度。

## 7. 开发必须新增的测量能力

### 7.1 时间戳和数据身份

控制内部时长必须使用 `std::chrono::steady_clock` 或等价单调时钟；另记ROS仿真时间，禁止混用二者相减。Unix时间只用于关联日志；跨机器关联需要校时误差预算，不默认两台机器时间完全一致。

每次策略更新至少产生一条不可拆分的记录：

```text
run_id, mode, stream_id, revision
physics_step_index, policy_sequence, source_packet_sequence, reference_frame_index
wall_start_ns, sim_start_ns
state_sample_wall_ns, reference_receive_wall_ns, reference_selected_time
redis_get_us, decode_validate_us, ack_us
state_estimation_us, observation_us, history_window_us
onnx_prepare_us, onnx_run_us, action_postprocess_us
command_commit_wall_ns, callback_end_wall_ns
physics_delay_queue_applied_frame, command_apply_wall_ns (仿真可观测时)
deadline_miss, stale_reference, invalid_packet, skipped_source_packets
trace_drop_count, fallback_reason
```

异步化后，Redis字段属于通信线程事件，以stream/序号关联，不再占策略线程。观测采样、动作计算、命令提交、模拟延迟后生效是不同时间点，必须分别命名。

2000 Hz基础循环无需同步写完整大CSV，但必须用低开销缓冲记录其耗时及每40步聚合：physics、readSim、state estimation、controller、writeSim、telemetry、剩余/等待。各分段必须说明是否嵌套，不能把父子跨度重复相加凑总时间。

### 7.2 输出指标与取证工具

- GMT开始间隔、有效动作提交间隔：均值、P50/P95/P99/P99.9、最大值、超20/22/25/40 ms次数。
- 一个策略任务从读取最新状态到命令提交的真实耗时；Run仅为其中一个子项。
- 每秒真实策略计数、仿真策略计数、RTF时间曲线、相对真实时间的累计相位偏差。
- 参考帧年龄、已验证缓冲水位、源包跳跃、重复消费、滞后动作和异常回退。
- 控制/物理/Redis/绘图/生成线程CPU占用与调度等待；固定窗口的上下文切换统计。
- 必要时使用perf、调度trace和ORT算子profiling；分别运行轻量验收与重型诊断，说明采集开销。

不能把 `rostopic hz`、GUI显示FPS、Redis发布频率、CSV写入频率或GPU利用率当作最终GMT控制频率的替代证据。

日志写盘与绘图放低优先级非控制线程，用有界队列；队列满时显式统计丢失的诊断数据，不能拖住控制。正式验收的核心周期记录不得静默漏样，否则该次结果无效。

## 9. 必须执行的对照试验

### 9.1 固定内容，避免把动作差异当性能差异

先用用户当前s190000、CUDA ONNX EP、DDIM20、CFG2.5、seed42、同一EDGE35特征和相同运动学/统计文件只生成一次qpos，保存其哈希。由这同一份qpos产生离线NPZ与在线参考，不要每次重新抽样生成舞蹈。

先剔除生成并发，以隔离消费链；最后恢复用户实际CUDA生成并发，验证资源竞争。所有结果明确列出生成EP与GMT EP，两者分别记录；完整音乐测试覆盖50～60秒转身段以及首尾边界。

| 编号 | 测试场景 | 想回答的问题 |
| --- | --- | --- |
| A | 同一世界，不加载机器人控制；安全离线仿真测试 | 物理环境自身成本 |
| B | 同一机器人站立、无GMT推理 | 基础物理/接触/控制/TF是否已经慢 |

### 9.2 数据与行为回归

1. 同源参考21×52逐帧比较，使用相同初始对齐、中心差分、窗口边界和关节顺序。
2. 录制相同机器人状态与历史，回放三个完整ONNX输入，比对优化前后actions。FP32路径建议初始 `atol=rtol=1e-5`；若改变后端或算法，误差阈值须单独评审，不能自动放宽。
3. Gazebo闭环检查关节跟踪误差、根姿态、触地稳定性、动作/力矩连续性、饱和和异常回退。两次闭环状态可能自然分岔，不要求全程位级相等，但不得用这个理由跳过受控输入回放。
4. 核查原实时、离线、buffered以及停止/返回的兼容性；缓存暂停不得继续按真实时间推进，实时模式不得在掉帧后无告警高速补发控制动作。

## 10. 真实50 Hz的建议验收标准

以下为本项目拟定的工程验收门槛，不是ROS/机器人通用标准或硬件安全认证；开发与控制负责人应在实施前确认。采用普通Linux时，目标是规定负载下有证据的软实时性能，不声称所有极端情况绝对无抖动。

### 10.1 正常工况

固定软硬件版本，预热完成后C～F各正式GMT场景连续运行至少10分钟、重复3次；短轨迹重启段另标，不能混入稳态。另做至少30分钟的代表性连续稳定测试。用户日常GUI/必要遥测和CUDA生成并发必须有结果；只在headless通过时应报告受限条件，不能宣称默认启动已经解决。

| 指标 | 建议门槛 | 防止的假达标方式 |
| --- | --- | --- |
| 有效GMT频率 | 10分钟平均49.9～50.1次/真实秒；每个完整1秒窗49～51次 | 不计重复发布旧动作，不用仿真时间分母 |
| 策略开始/命令提交间隔 | 两者均统计；`abs(间隔-20ms)` P99≤1ms，P99.9≤2ms；最大间隔≤25ms | 不能连续快算再长时间停顿凑平均 |
| 策略任务完成耗时 | 从本次状态读取到新动作提交P99≤15ms，正常验收中不得出现≥20ms的任务 | 保留约5ms余量；区别“任务耗时”和“相邻调用间隔” |
| Gazebo实时率 | 全程RTF均值0.999～1.001；1秒窗0.98～1.02，标注首尾采样边界 | 只保证控制线程50次，但物理仍慢，不通过 |
| 仿真/真实累计偏差 | 去掉启动固定偏移后，10分钟内绝对偏差≤100ms | 频率平均近似合格，但音乐持续漂移，仍不通过 |
| 新动作与状态身份 | 每次动作对应明确观测/历史/参考序号；旧推理结果不能冒充新动作 | 固定定时器输出同一动作不算有效推理 |
| 当前状态新鲜度 | 开始构造本次观测时，最新关节/IMU采样年龄P99≤2ms、最大≤5ms；历史输入按既定历史契约处理 | 高频读取一份陈旧状态不能算有效闭环 |
| 实时参考交付 | 在控制帧截止前拿到正确参考；经已声明固定缓冲对齐后中心帧误差≤1个50Hz帧 | 大缓冲掩盖不断累积的落后不通过 |
| 有效缓冲 | 正常工况无断供，无未声明的丢帧补偿；迟到/重复/拒绝全部可计数 | 不能静默跳过困难动作 |
| 数值与跟踪 | 同源回放通过第9节；完整舞蹈无新增异常回退/明显转身错位 | 用模型或数据变化换性能不通过 |
| 可观测性 | 核心周期记录无漏样，日志不覆盖，附版本与哈希 | 不能只交一个平均Hz截图 |

“间隔超过20 ms”与“策略任务耗时超过20 ms”要分开计数：一个周期任务算得很快，也可能因调度稍晚开始；前者由抖动指标约束，后者属于计算完成超期。

物理基础步仍为0.5 ms时，应统计真实每40步的总推进时间，不强求同步架构中包含GMT推理的那一个物理步也在0.5 ms内完成。若将来要保证实机500 Hz底层循环每2 ms完成，那是另一项更严格的执行/推理隔离验收，不能沿用这个放宽条件。

### 10.2 音乐同步与完整时长

真正RTF≈1后，仍要验证音频设备/播放器延迟及动作起始偏移。以音频实际播放位置和参考中心帧的时间坐标对齐，先标定固定启动偏移；建议正常播放期间相位误差P99≤40 ms、最大≤60 ms，且无持续累积漂移。

只统计“20ms定时器tick”不是完成证明；必须用实际消费帧/动作时间与音频位置测量。以本离线3301帧轨迹为例，报告从有效首帧到有效末帧的真实耗时是否接近66.00秒，并单列准备、缓入、返回和尾部保持。buffered当前关闭音频，若未扩展音频流程，只能完成控制/仿真验收，不能填写音乐同步“通过”。

模拟9ms执行延迟与音频固定偏移应明确列入延迟预算，不能从记录中隐去。不要通过改变音乐速度掩盖系统实时率不足，除非用户另行选择慢速同步模式。

### 10.3 超载与异常

超过门槛时必须有可定位的计数和告警；连续超期、参考过期、断连及无效输出的退出/保持/返回策略由控制负责人评审。维持已批准的保护边界，不自行设计未经动力学验证的急停轨迹。

验收至少覆盖：迟到结果不会应用到错误帧；Redis无响应不能无限阻塞控制；掉线不会继续无期限执行陈旧动作；不会用突发追帧加速机器人；仿真暂停/恢复不会混用旧stream。故障测试不要求仍达到50 Hz，但要求失效可控、原因可见，且不能把故障时段静默从报告删除。

## 11. 实机边界：不是同一条底层路径

当前仿真通过Gazebo世界更新回调驱动controller_manager；实际硬件另走 `B/legged_hw/src/LeggedHWLoop.cpp` 的独立循环线程，使用真实经过时间，并尝试设置SCHED_FIFO，失败会告警。

实机launch当前配置为基础500 Hz、decimation10；`R/bumi_hw/legged_bumi_hw/src/BumiHW.cpp` 调用 `HwController::Init`、`rt_ethercat_get_data`、`SetMitCmd`、`rt_ethercat_set_command/run`。这确认了硬件接口存在EtherCAT路径，但本次没有实机进程、总线周期或电机回执测量，也没有据此确认底层每个设备的有效更新率。

因此不能说“ROS网络把电机卡成了29 Hz”，也不能说“Gazebo慢证明真实机器人也只有29 Hz”。应分别交付：仿真真实50 Hz报告，以及需要实机团队另测的500 Hz底层周期/50 Hz策略、总线往返、有效命令与保护报告。

## 14. 最终结论

当前应准确反馈为：**GMT所在的Gazebo部署闭环曾出现真实执行频率明显低于配置50 Hz的问题，在线参考与慢仿真的时间轴不一致；底层缺少完整的周期预算、通信隔离和分段计时，需要优化并重新验收。**

已查到的优先排查点是2000 Hz循环中的遥测/TF与动态分配、同步Redis关键路径、线程竞争和物理/接触成本。实际GMT模型裸Run本次很快，不足以支持“模型自己算不动50 Hz”的结论。接手者应先量化占比，再优化主要耗时；保留数据与控制语义，最终用真实周期、动作有效性、RTF和音乐相位共同证明问题已解决。

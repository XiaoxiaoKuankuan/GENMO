## 一、目前最主要的问题

当前实机部署把硬件读取、策略计算、参考数据接收和硬件写入放在同一个控制循环里。中间任何一步变慢，后面的工作就要一起等。

所以，配置写了“底层500 Hz、策略50 Hz”，不代表实际一定能做到。现在最需要解决的是：**让必须按时执行的硬件控制，不被策略计算、网络等待和调试工作拖住。**

从代码已经能确认这种串行结构。各部分实际占了多少时间、实机是否已经超时，还需要分别计时，不能只凭结构对比宣布所有卡顿都由某一项造成。

## 二、与SONIC G1部署的主要区别

当前GMT实机流程：

这里的500 Hz指部署程序的实机基础循环，不是电机内部控制频率。当前Gazebo仍为500 Hz、分频10，关闭绘图/CSV；用户反馈WALK/GMT均异常后，已撤回此前实验性隐式PD，恢复原显式计算。基础周期已在DEFAULT模式确认，但两种策略跟踪和真实50 Hz尚未验收。这不改变下述实机串行调用结构，详见[PD恢复与公共链路核查](gmt_explicit_pd_restore_20260907.md)。

```text
同一个500 Hz循环：
读硬件状态 → 更新控制器 → 写硬件指令 → 等待下一次

其中每10次更新控制器时，还要完成：
接收参考数据 → 整理策略输入 → GMT推理
```

这意味着：本来应该每2毫秒完成一次硬件循环，但遇到策略计算或通信等待时，这一次循环可能被拉长。即使策略计算小于20毫秒，也不代表它能塞进2毫秒的底层周期。

SONIC G1的做法：

```text
策略线程：每20毫秒计算一次目标 → 放入缓存
发送线程：每2毫秒读取最新目标 → 发送给机器人
```

两件事由不同线程负责，不要求发送线程每次先等策略算完。它减少了策略计算对命令发送的直接阻塞。

**可以据此明确提出GMT的改进方向：将策略计算与底层硬件控制分开。** 但分线程本身不是验收结果，还要处理共享数据、迟到结果和过期指令；持续发送旧目标不等于策略达到了50 Hz。

当前GMT使用ROS1，并通过Redis接收在线参考；SONIC G1通过Unitree SDK2/DDS发送机器人指令。这些名称本身不能说明谁快谁慢。本次对比确认的是工作如何分配、哪些地方必须等待，不是“用了ROS1就一定慢”。

## 三、需要解决的具体问题

### 1. 策略计算会阻塞硬件控制循环

**现在是什么样：** GMT推理在控制器更新函数内部同步执行，没算完就不能继续完成本次硬件写入，也会推迟下一次硬件读取。

**可能造成什么影响：** 硬件指令发送忽快忽慢；策略推理耗时稍有波动，就可能影响底层控制节奏。

**需要怎么优化：** 参考SONIC的分工，将策略计算与硬件读写/命令发送隔离。通过缓存交接完整结果，明确结果对应哪次状态、什么时候算完、什么时候允许使用。不能为了分线程，默认给所有动作额外增加一帧延迟。

### 2. 在线模式下，会同步等待Redis

**现在是什么样：** 控制器更新时直接向Redis取参考数据，并发送确认消息。请求、接收和确认需要等待完成，然后才能继续后面的工作。当前接收代码未发现明确设置网络读写等待上限；已有“数据是否过期”的检查，并不等于网络请求一定及时返回。

**可能造成什么影响：** Redis响应慢、连接异常或重连时，控制流程可能跟着等待。这里的问题不只是数据量大不大，而是“网络等待占着控制线程”。

**需要怎么优化：** 单独接收、校验和缓存参考数据；控制循环只取已经准备好的有效数据。连接、重连和确认消息不要占住控制循环。无数据或掉线时按明确的保护规则处理，不能无限等待或无限使用旧数据。

### 3. 日志、调试发布和反复申请内存占用了控制时间

**现在是什么样：** 基础控制循环中同时准备和发布多种调试数据、机器人姿态/关节坐标信息，并反复创建数组、消息和关节映射。仿真中，很多工作仍跟着基础循环执行（当前500 Hz，原2000 Hz），尚未隔离；关闭绘图/CSV节点没有移除这些上游工作。

绘图和CSV写盘在另一个节点，但控制循环里高频准备、发布数据的工作仍然存在；不能只降低CSV记录频率，就认为上游开销也降下来了。

**可能造成什么影响：** CPU忙于非控制工作；每次循环耗时不稳定。机器人显示、绘图和记录数据可能影响真正的控制任务。

**需要怎么优化：** 调试数据按需要降频，日志异步写入，不需要更新的固定坐标信息不要反复发布。常用数组和消息提前准备，减少控制过程中反复申请、释放内存。保留必要监控，不能通过删除保护检查提速。

### 4. 多个线程可能互相抢占CPU

**现在是什么样：** 策略计算、通信、仿真和调试程序同时运行。即使整机CPU占用不高，关键控制线程也可能没有及时获得执行机会。现有线程配置不能证明这些任务互不影响。

**可能造成什么影响：** 单独测试很快，放到完整部署中却偶尔卡一下；平均频率接近目标，但某几个周期明显超时。

**需要怎么优化：** 先查看各线程真正的运行和等待时间，再安排控制、推理、通信和日志的线程数量、优先级及CPU分配。不能简单把所有线程都设成最高优先级。

这一项目前属于需要测量的风险，尚未确认谁抢占了谁、造成了多大延迟。

### 5. 硬件读写和总线通信也会消耗时间

**现在是什么样：** 实机每次循环都要读取状态、准备指令并调用硬件SDK收发。它们与控制器更新串在同一个循环中，不是没有成本。

**可能造成什么影响：** 即使策略计算很快，硬件或总线响应慢，也可能让整个循环超过2毫秒。

**需要怎么优化：** 分开记录硬件读取、控制器更新、硬件写入和总线等待的耗时，核对SDK实际运行节奏。必要的硬件工作不能省略，但不能让异常等待无限拖住控制。哪些工作可以异步处理，需要结合SDK和控制安全要求决定。

目前没有实机总线耗时数据，不能直接说“总线已经被证明很慢”。

### 6. 缺少直接判断“实际有没有按时完成”的记录

**现在是什么样：** 能看到配置频率和部分运行记录，但缺少把每次硬件循环、策略计算和通信等待完整串起来的计时。实机已有周期超时告警，仍不足以解释时间具体花在哪里。

**可能造成什么影响：** 只能知道“效果不对”或“运行偏慢”，却难以区分是计算慢、网络等待、硬件等待，还是线程没有及时运行。

**需要怎么优化：** 记录实际周期、各环节耗时和超时次数；出现卡顿时能定位是哪一步。不能用发送旧指令的次数、绘图刷新次数或配置里的50 Hz代替实际新策略输出频率。

## 四、仿真和实机要分开判断

Gazebo还需要计算物理仿真，这部分计算负担在真实机器人上不存在。2026-09-07将物理/基础控制从2000 Hz调为500 Hz，随后试验过隐式PD；用户反馈WALK/GMT均异常后要求撤回，当前是原显式PD、500 Hz/分频10，绘图/CSV关闭。

已确认的周期耦合包括站立过渡写死1000个循环，现已按秒计时。隐式PD曾改善固定机身定姿指标，但没有证明WALK/GMT闭环等效，已从生产撤回；不能用定姿实验宣布两种策略的异常根因已经解决。现保留模型和原PD，继续核查共有的反馈周期、策略更新、动作保持和命令延迟。

此前隐式版在无GUI、Bridge和Redis条件下，66仿真秒用了72.4569真实秒，实际新策略平均45.5443 Hz；这是历史实验，不能代表当前恢复版，也不能与有GUI的buffered耗时作严格A/B。后续仍需在统一负载下分段测量、隔离控制/推理/通信/诊断开销，同时验收动力学稳定性。

**降低Gazebo频率不能替代部署框架优化。** 实机上位控制循环本来就配置为500 Hz；策略阻塞、同步Redis、调试开销和硬件等待等问题，仍需要在各自路径中检查。

也不能反过来说“仿真慢，所以实机肯定慢”。仿真性能和实机控制周期应分别提供结果。

## 五、希望最终达到什么效果

1. 在约定的运行负载下，硬件读写/命令发送稳定按500 Hz执行，策略稳定按50 Hz产生新结果，两者不因串行等待而互相拖慢。
2. Redis、日志和绘图发生延迟时，不把整个底层控制流程卡住。
3. 出现超时、掉线或无效结果时，有明确告警和已评审的保护处理，不长期执行陈旧指令。
4. 优化前后都有实际时间记录：一次硬件循环用了多久、两次新策略结果相隔多久、最慢的一次卡在哪里。
5. 保持原有动作含义、控制参数和保护规则；不能通过删检查、重复旧动作或增加未说明的延迟来凑频率。

验收看真实运行时间：硬件循环目标间隔2毫秒，新策略结果目标间隔20毫秒。既看平均值，也看最慢周期和超时次数；仿真还要确认能跟上真实时间。
